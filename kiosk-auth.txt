## Core security problem

At present, `/api/kiosk/call/token` can be called without device authentication.

The backend verifies that a requested phone number is allowed, but it does not verify that the request came from a legitimate physical TalkBox.

We need to introduce a device identity layer.

The intended rule is:

**The TalkBox website is public. Telephone privileges are not.**

A random visitor to `talk-box.org/kiosk` should be able to:

* browse resources
* search resources
* use voice search
* view 211 information
* interact with the normal TalkBox UI

but should NOT be able to initiate a real PSTN call.

An enrolled physical TalkBox should get all of those functions plus real Twilio calling.

## Desired architecture

Implement this model:

`browser -> talk-box.org/kiosk -> Vercel -> /api -> Fly FastAPI -> device auth -> Twilio`

Permanent Twilio credentials must remain only on Fly.

Do not expose the following to the browser:

* Twilio API key secret
* Twilio auth token
* Twilio account credentials
* Neon database credentials
* backend API secrets

The browser may continue receiving the existing short-lived Twilio Voice Access Token after authorization.

## 1. Add kiosk device persistence

Add a new Alembic migration and persistence model for physical TalkBox devices.

A sensible table would be `kiosk_devices`.

At minimum support:

* UUID/internal id
* human-readable device code such as `TB-001`
* display name
* location/site text
* credential hash
* enabled boolean
* created_at
* updated_at
* last_seen_at
* revoked_at nullable

Do NOT store reusable plaintext device credentials in Neon.

Generate credentials using cryptographically secure randomness.

Store only a strong cryptographic hash of each device credential.

Design this so individual devices can be revoked without changing credentials on every other TalkBox.

## 2. Implement device authentication

Create a small, isolated backend device-auth module rather than mixing device authentication into the existing user/admin authentication system.

Physical TalkBoxes are machines, not human users.

Use a cookie-based approach because frontend and `/api` are same-origin through Vercel.

Preferred design:

* Secure
* HttpOnly
* SameSite appropriate for same-origin production
* long-lived but revocable device credential
* browser JavaScript should not need to read the secret value

Requests to protected kiosk endpoints should resolve the cookie into a valid, enabled `kiosk_devices` record.

Update `last_seen_at` periodically or opportunistically without creating excessive DB writes.

A stolen/revoked device credential must stop working.

## 3. Add device enrollment

Create a secure enrollment workflow for preparing a new physical tablet.

Desired operator workflow:

1. Factory reset / prepare tablet.
2. Open `talk-box.org/kiosk`.
3. Technician enters enrollment mode.
4. Technician supplies a short-lived / one-time enrollment code generated by an authenticated administrator.
5. Backend creates or activates the device.
6. Backend returns the device credential as an HttpOnly Secure cookie.
7. Tablet becomes an enrolled TalkBox.
8. Normal users never need to log in.

Do not make the permanent device credential manually copy/pasteable as the normal deployment workflow.

Enrollment codes must:

* expire
* be single-use
* be random enough to resist guessing
* be invalidated immediately after successful enrollment

It is fine to create a separate persistence table for enrollment tokens if that results in a cleaner design.

## 4. Add device status API

Add an endpoint such as:

`GET /api/kiosk/device/status`

It should return only non-sensitive information such as:

* enrolled
* enabled
* device code
* display name
* location
* calling_enabled

For an anonymous browser it should return something equivalent to:

* `enrolled: false`
* `calling_enabled: false`

Do not make merely loading `/kiosk` require authentication.

## 5. Protect telephone-authorizing endpoints

Require a valid enrolled and enabled TalkBox for:

* `POST /api/kiosk/call/token`
* `POST /api/kiosk/call/start`

Do the device authorization check before issuing any Twilio capability.

Return a clear `403` for anonymous, disabled, revoked or invalid devices.

Do NOT protect basic resource endpoints solely because the browser is not enrolled.

These should remain public unless there is a compelling existing security reason otherwise:

* `/api/kiosk/config`
* `/api/kiosk/query`
* `/api/kiosk/directory`
* `/api/kiosk/speech/transcribe`

## 6. Preserve the existing Twilio model

Do not replace the existing browser Voice SDK design.

Continue to:

* generate short-lived Twilio Access Tokens on the backend
* validate destinations server-side
* use the backend TwiML route
* validate Twilio webhooks
* keep Twilio secrets in Fly secrets

The device credential authorizes the backend to issue a Twilio token.

The device credential itself is NOT a Twilio credential.

## 7. Fix Twilio status webhook verification

Review the current `/api/kiosk/call/status` endpoint.

It currently appears to accept webhook data without validating `X-Twilio-Signature`.

Apply the same appropriate Twilio signature-validation strategy used for the TwiML webhook.

Do not trust arbitrary internet POSTs as Twilio callbacks.

## 8. Tighten CORS

For production, configure a restrictive allowlist for legitimate TalkBox origins where practical.

Preserve localhost development.

Avoid breaking Vercel preview/local development unnecessarily.

Document the resulting environment variables.

## 9. Add basic abuse protection

Implement sensible backend defenses around call-token creation.

At minimum:

* rate limit token issuance by device
* one active/connecting call per device if practical
* prevent rapid repeated requests
* log rejected attempts
* identify the device in call-related logs

Keep this simple and understandable.

Do not introduce Redis or another infrastructure dependency unless the existing architecture truly requires it.

Database-backed or lightweight in-process protections are acceptable for this phase, but document limitations.

## 10. Keep current dialing policy for this change

Important: do NOT quietly broaden outbound calling while implementing device authentication.

The current system deliberately limits calls to approved agencies / built-in numbers / configured test numbers.

Keep that behavior for this PR.

Device enrollment is a prerequisite for potentially enabling general US calling later, but that is a separate policy change.

Do not implement arbitrary dialing unless you find existing requirements explicitly contradicting this instruction.

## 11. Update frontend behavior

`/kiosk` should load for everybody.

For an enrolled physical device:

* existing kiosk UX should remain essentially unchanged

For an anonymous browser:

`/demo` must remain simulated and must never make real PSTN calls.

Do not let an enrolled-device cookie accidentally make `/demo` place a real call.

## 20. Acceptance criteria

This feature is complete when all of these are true:

1. `talk-box.org/kiosk` loads from an ordinary laptop browser.
2. That laptop can browse/search TalkBox resources.
3. That laptop cannot obtain a usable Twilio calling token.
4. An administrator can generate a one-time enrollment code.
5. A physical tablet can use the code once and become `TB-xxx`.
6. The device receives a Secure HttpOnly credential.
7. Refreshing/rebooting the tablet preserves enrollment.
8. The enrolled tablet can obtain a short-lived Twilio Voice token for an allowlisted number.
9. Revoking the device from `/admin` prevents further calls without modifying Twilio credentials.
10. `/demo` remains fake/simulated regardless of enrollment.
11. No permanent Twilio or database secrets are visible in browser JS, localStorage, cookies readable by JS, or the repo.
12. Existing kiosk/search/admin functionality still works.
13. Tests pass.
14. Migration runs cleanly against Neon.
15. Production configuration is documented.
